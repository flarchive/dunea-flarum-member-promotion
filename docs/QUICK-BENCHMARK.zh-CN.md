# 快速性能压测记录

执行日期：2026-10-11。

## 环境与数据

- Docker Desktop，24 vCPU、约 23.2 GiB 可用内存、`overlayfs`；容器未设置独立 CPU/内存上限；
- PHP 8.4.21、Flarum 1.8.19、MariaDB 10.11.19；
- 单个 CLI worker，数据库和 Flarum 位于同一 Docker Desktop；
- 10001 个用户（含初始管理员）、10000 个主题、100000 条帖子；
- 有效回复计数总和 90000；
- 3 条连续阶段规则，批大小 1000，单次命令时间预算 300 秒。

该环境用于快速发现复杂度、写放大和任务恢复问题，不代表生产服务器，也不能直接线性外推到百万用户。

## 结果

| 场景 | 处理量 | 总墙钟时间 | 墙钟吞吐 | 失败 |
| --- | ---: | ---: | ---: | ---: |
| 冷启动回复计数重建 | 10001 用户 / 100000 帖子 | 51.889 秒 | 约 192.7 用户/秒 | 0 |
| 首次三阶段晋级扫描 | 10001 用户 / 26986 次授予 | 146.446 秒 | 约 68.3 用户/秒 | 0 |
| 已有身份的稳态重扫 | 10001 用户 | 37.801 秒 | 约 264.6 用户/秒 | 0 |

首次晋级扫描产生 26986 条 grant、26986 条 success 审计日志；grant 唯一键计数与总数一致。包含初始管理员组在内，`group_user` 总数与去重后数量一致，没有重复关系。29 个未到注册时长的用户被安排到未来复检，压测结束时到期待办为 0。

MariaDB 未启用 statement digest consumer，因此使用全局 `Questions` 差值作为上界观察值；该数值包含 Docker 健康检查和压测控制查询：首次晋级约 277097，稳态重扫约 60566。稳态结果约为每用户 6.06 条数据库语句，与 4 条核心评估查询加待办认领/完成操作一致。

## 压测发现并修复的问题

未达到注册时长的用户在处理当前待办时，未来复检原先会与当前已认领记录合并为立即执行，导致同一批内重复占用处理名额。现改为：评估阶段只计算最早复检时间，worker 使用原 claim token 原子完成当前待办或改期。回归测试确认立即再次运行不会重新认领该用户。

压测数据生成器也补齐了 Flarum 1.8.19 必填的 `users.password` 和 `discussions.slug` 字段。

## 配置建议

生产运行参数现已固定为每批最多 100 个用户、单次最多 20 秒，后台和 CLI 均不开放覆盖参数。应持续观察数据库 CPU、磁盘延迟、行锁和待办增长；若队列长期无法收敛，优先排查调度器、失败任务和慢查询。大型计数重建应在低峰期执行。
