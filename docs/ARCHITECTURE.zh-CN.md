# 架构、恢复与调优

## 数据流

正文回复事件只做常数级计数更新和 `user_id` 去重入队。每分钟调度命令先推进一个稳定游标后台任务，再认领到期用户并评估。注册时长尚未满足时，待办记录直接移动到阈值时刻，不做每分钟轮询。全量扫描使用主键游标和批量待办写入；同一批用户复用启用规则及目标组元数据，每个用户一次预取历史授予和人工阻止，避免按规则产生 N+1 查询。

主要表：

- `member_promotion_rules` / `rule_versions`：当前规则和不可变条件快照；
- `counters`：有效回复缓存及 initialized 门禁；
- `discussion_users`：不依赖帖子存续的主题参与者索引，供主题隐藏、恢复和级联删除后分批纠偏；
- `pending`：按用户主键合并的待检查集合；
- `jobs`：全量扫描、计数重建、主题可见性变化；
- `grants`：插件确认执行过的授予来源；
- `blocks`：人工撤销后的自动恢复阻止；
- `logs`：记录实际晋级、人工阻止和失败等状态变化，不为每次无变化的检查写日志；
- `runtime`：心跳、最近统计和最近错误。

规则图把“前置组 → 目标组”视为有向边。启用规则不能形成任意长度的环，也不能有多个规则授予同一目标组。拓扑层内按 `priority DESC, id ASC`，因此结果稳定。

## 并发与恢复

- 任务认领写入随机 claim token；5 分钟无心跳可由其他进程接管。
- 用户晋级事务锁定 `users` 行。`grants(user_id, rule_id, rule_version)` 唯一约束和 `group_user` 唯一关系共同防重。
- 每个任务页成功后提交 cursor；中断最多重做当前页，不跳过后续数据。
- 单用户失败只增加该用户 attempts，指数退避；三次后停止。任务同样最多三次。
- 新的用户事件会重置该用户失败待办的重试状态，避免永久积压不可执行记录。
- PHP 进程锁 `withoutOverlapping` 是第一层优化，数据库 claim/唯一约束才是多进程正确性的保障，不依赖共享 Redis cache。

## 规则修改一致性

每次保存产生新 version 和完整快照。数值调整会创建只针对该规则的后台扫描。已有目标身份不重复记录。若规则目标组变更，旧 active grant 被视为历史结构完成，不会把历史成员自动搬到新组；应复制为新规则来表达新流程。

被后续阶段明确移除的前置身份将其 grant 标记为 `consumed`。之后即使前置规则升版或降低门槛，该阶段仍视为已完成，不会把已经消费的低阶段组重新加回。全局自动晋级关闭时，扫描任务和用户待办保留而不执行；计数重建及主题可见性纠偏仍可推进。管理员 dry-run 仍可预览规则结果。

## 回复计数

帖子创建/隐藏/恢复/删除和审核通过执行原子增减。计数行不存在时只标记未初始化，不用错误的默认 0。主题参与者索引在回复创建和用户计数重建时维护；主题隐藏、恢复或外键级联删除后按参与用户 ID 游标使计数失效，再于正常用户待办处理前重建。

删除回复或提高门槛只影响后续判断，不撤销已有身份。

## 运行参数与观察顺序

1. Worker 固定每批最多处理 100 个用户、单次最多运行 20 秒，后台和 CLI 均不开放覆盖参数；
2. 启用后至少观察三天，查看 `member-promotion:status` 的 pending、单批处理量、数据库 CPU 和锁等待；
3. pending 短期增长属于全量扫描的正常现象；若长期无法收敛，应先检查调度器、失败任务、慢查询和数据库资源，不通过放大单批参数掩盖问题；
4. 大型计数重建避开备份和业务高峰；
5. 日志保留默认 90 天。日志和已完成任务均按小批次清理，避免大表一次性删除造成长事务或锁峰值；清理不会破坏幂等或人工阻止状态。

扩展没有给 Flarum 核心表增加索引。查询依赖核心已有的 users 主键、posts 主键/作者/讨论索引和 `group_user` 组合关系；扩展表索引均对应实际认领、过滤、来源和时间游标查询。
